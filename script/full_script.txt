1. Understanding the Databricks Lakehouse
Before we run the project, it helps to map Databricks to the "typical company data environment" most data engineers inherit. A typical company data stack has several moving parts:
1. Data Sources
Operational databases (e.g., Postgres/MySQL), SaaS systems (e.g., Salesforce, Stripe), logs, and sometimes event streams (e.g., Kafka/Kinesis).
These systems generate data in multiple shapes: structured tables, semi-structured JSON, files, and events.
2. A landing / raw zone (usually on object storage)
Raw data is commonly landed in cloud object storage (S3 / ADLS / GCS). Object storage is a cloud storage system designed to store large amounts of data as files ("objects"), rather than as rows in database tables. Teams use it because it is cheap, highly scalable, and can store any format (CSV, JSON, Parquet, images, logs, etc.). 
3. Table Layer:
To make data in object storage usable for analytics and downstream processing, a table layer is added on top using open table formats such as Delta Lake, Iceberg, or Hudi. Its purpose is to turn raw files in storage into reliable, queryable tables. Instead of treating object storage as "just a folder of files" (for example, months of JSON transaction data), the table layer adds transactional metadata and schema rules so the data behaves like a database table: consistent queries, enforced and evolvable schemas, and reliable reads and writes.
Interlude: The Medallion Architecture (Bronze → Silver → Gold)
Once you have a table layer, you still need a consistent way to organize tables. In Databricks, many pipelines follow the Medallion Architecture, which improves data quality and usability in stages:
i. Bronze (Raw): A direct copy of your raw data (CSVs, JSON, logs) loaded into a Delta table. Minimal transformation; you mainly capture and preserve the input. If downstream transformations or business logic change, you can replay from Bronze without going back to the source system.
ii. Silver (Cleansed & Conformed): This is where data is cleaned and standardized: types are fixed (e.g., timestamps are actual timestamps), records are deduplicated, and quality rules are enforced (e.g., "fare_amount ≥ 0"). Silver is commonly treated as the main clean layer that downstream analytics and ML build on.
iii. Gold (Curated/Aggregated): Business-facing tables for reporting and consumption. Silver data is shaped into metrics (e.g., "daily revenue by cab type") that are ready for dashboards and common queries. Gold is typically more read-optimized and more opinionated (aligned to business definitions) than Silver.
4. Metadata + Governance (Catalog/Metastore):
Metadata tracks what tables in the table layer exist, their schemas, where they physically live in storage, and who is allowed to access them. The full repository of metadata is known as the metastore or catalog. In Databricks, Unity Catalog provides this function: the metastore is the top-level container that registers metadata for data and AI assets and enforces the permissions that govern access to them.
5. Compute to transform data (batch and/or streaming):
Compute is the execution layer of a data system: the CPU, memory, and runtime processes that actually execute code to read data, apply transformations, and write results. In Databricks, this compute is primarily provided by Apache Spark running on clusters. Spark is used to clean, standardize, join, and aggregate raw data from object storage into curated table-layer datasets that can be queried by downstream consumers.
This compute runs on clusters (multiple machines working in parallel) rather than a single virtual machine, which allows Databricks to process large datasets efficiently in both batch and streaming workloads.
6. Orchestration + monitoring
Pipelines need scheduling, dependency management, retries, alerting, and audit logs (what ran, when, and what happened). Common external tools include Airflow and Dagster; Databricks also provides native surfaces for this (Jobs/Workflows and DLT/Lakeflow pipelines).
7. A serving/analytics layer
This is where analysts and BI tools query curated datasets (often Silver/Gold). Many teams call this "the warehouse," even if the data still lives in object storage (for example, queried through Databricks SQL).
In practice, teams assemble these pieces either as managed cloud services or self-hosted services.
2. How Does This All Run and Function Together?
The surrounding services (catalog, orchestration, monitoring) can run in a few different ways: as managed cloud services, on virtual machines, or as containerized workloads. Kubernetes is one common way to run containerized services at scale, but it is not required for a data environment to be distributed - distribution comes from the compute engine and storage architecture, not from Kubernetes itself.
Example (a simple Kubernetes-based setup)
Imagine a small UK bike retailer that runs most internal systems on Kubernetes. Their website and inventory services are containerized, but if we zoom in specifically on the data environment, it would look something like this:
Sources: orders/customers in Postgres; inventory events; web analytics; ad spend exports; optional event stream.
Storage: raw extracts land in object storage.
Tables: raw becomes Bronze; cleaned/conformed becomes Silver; business aggregates become Gold (implemented via a table format like Delta/Iceberg/Hudi).
Catalog: tracks tables, schemas, locations, permissions.
Compute: Spark/SQL transforms and updates tables (batch or streaming).
Orchestration: schedules and monitors ingestion + transformations.
Serving: curated Silver/Gold tables are queried by analysts/Power BI via a SQL endpoint.

Where Databricks Comes in
Databricks bundles and manages much of the stack you would otherwise assemble yourself - table/storage format, distributed compute, pipeline execution, governance, and the SQL serving surface - into one platform, built around Apache Spark, Delta Lake, Delta Live Tables, and Unity Catalog.
Delta Lake (storage + tables)
Delta Lake is the open table format used by Databricks for Bronze/Silver/Gold tables. The table data lives as files in cloud object storage (S3/ADLS/GCS), and Delta Lake's transaction log records changes so you get database-like reliability (ACID transactions, versioning/time travel).
Ingestion tooling (getting data into Bronze)
Databricks provides ingestion components that standardize common ingestion patterns. Auto Loader is a common example: incremental file ingestion from cloud storage into a Bronze table (new files are picked up automatically, schema evolution can be handled, and ingestion state is tracked so you do not reprocess the same files repeatedly). In this project, Auto Loader is one Bronze option; the other option is ingesting from an existing table/source already present in the environment.
Apache Spark (distributed compute)
Apache Spark is the distributed compute engine that performs ingestion and transformations. This is where clusters come in: Spark distributes work across multiple machines so you can process large datasets in parallel (batch and streaming). Depending on workspace configuration, compute can run on user-managed clusters or Databricks-managed/serverless compute.
Delta Live Tables (DLT)
Delta Live Tables (DLT) is Databricks' managed pipeline framework. Instead of hard-coding execution order ("run step 1, then step 2"), you define the target tables and their derivations. The platform infers and executes the Bronze → Silver → Gold dependency graph. 
- Databricks builds and runs this graph, manages incremental processing - meaning only new or changed data is processed on each run, with state and progress tracked via checkpoints where applicable - and enforces data quality expectations as part of the pipeline definition.
Expectation actions are explicitly configured: 
-Fail update (stop the pipeline)
-Drop row (exclude invalid records)
-Log only (record violations while continuing processing)
Unity Catalog (governance + metadata)
Unity Catalog is the governance and metadata layer: it defines catalogs and schemas, stores table metadata, and enforces permissions (who can read/write what). Conceptually, it replaces a standalone metastore/catalog and centralizes access control across workspaces and compute.
Databricks SQL (serving/analytics)
Databricks SQL (via SQL Warehouses) is the serving surface for fast SQL queries over governed Delta tables. Unity Catalog governs what you can see and do; Databricks SQL is the query endpoint analysts and dashboards use to access curated Silver/Gold datasets. Key point: in Databricks, "warehouse" usually refers to the SQL warehouse (a compute endpoint), while the data itself lives in governed Delta tables.

Putting it together (one end-to-end flow)
Ingest into Bronze Delta tables → transform into Silver/Gold Delta tables using Spark + managed pipelines → serve curated tables through Databricks SQL, with Unity Catalog enforcing governance and providing metadata across the environment.
Same Kubernetes Example With Databricks Instead
If we take the same UK bike retailer, the external sources do not change (e-commerce DB, inventory DB, web/ad/support systems, optional Kafka/Kinesis streams). What changes is that Databricks becomes the central platform that standardizes how those pieces are operationalized:
Landing (object storage)+ Bronze: raw data still lands in S3/ADLS/GCS, but ingestion writes into Bronze Delta tables (often using Auto Loader for incremental file pickup).
Table layer: data is modeled as Delta Lake tables across Bronze → Silver → Gold (raw → cleaned/conformed → business aggregates).
Governance: Unity Catalog stores table metadata and enforces permissions (e.g., analysts query Gold but not raw PII in Bronze).
Compute + orchestration: transformations run as Spark jobs on Databricks, operationalized via Jobs/Workflows and/or Delta Live Tables (part of Lakeflow pipelines).
Serving: analysts and BI tools query curated tables through Databricks SQL using a SQL warehouse (compute endpoint), with Unity Catalog controlling access.

Net effect: the retailer still has external sources and object storage, but Databricks consolidates the operational pieces into one governed workflow aligned to the same Bronze/Silver/Gold lifecycle.
3. Is Databricks Low Code?
Strictly speaking: yes and no.
It is not "low code" in the sense that you can avoid programming. For non-trivial pipelines you still write SQL, and often Python/Scala for transformations, validation, testing, and integration. What Databricks reduces is operational friction: you spend less time wiring infrastructure, and more time on data logic. It standardizes and automates common concerns like compute provisioning, autoscaling, incremental execution patterns, and pipeline/job monitoring.
Example pipeline (very typical)
Source A: clickstream events (streaming)
Source B: orders/customers in Postgres (batch or CDC)
Goal: daily metrics (conversion, revenue by category, drop-off pages) with basic quality rules (required IDs, valid timestamps, no negative revenue)

Traditional approach (many components)
In a traditional stack, this pipeline is usually built by assembling and operating a toolchain such as:
Kafka or Kinesis for clickstream ingestion
Debezium or custom jobs for Postgres CDC
Object storage (S3 / ADLS / GCS) for raw data
Spark jobs for transformations
A table format (Delta / Iceberg / Hudi) configured and managed manually
Airflow or Dagster for orchestration and dependencies
A metastore or catalog for table metadata
Separate data-quality checks (custom code or a framework)
A warehouse or query engine for BI access

Each tool does its job, but all integration points are owned by the team: IAM and networking, schema and state management, retries and backfills, upgrades, observability, and failure handling across systems. This typically results in slower delivery and significantly higher operational overhead, in exchange for greater flexibility and direct ownership of the stack.
Databricks approach (same outcome, fewer moving parts)
Databricks consolidates most of that into platform features: ingestion (Auto Loader/streaming), transformations (Spark SQL + Python), managed pipelines (Delta Live Tables as part of Lakeflow pipelines + Jobs), storage (Delta Bronze/Silver/Gold), governance (Unity Catalog), and serving (Databricks SQL).
So you get simpler operations, but you have to accept Databricks' conventions and managed abstractions.
4. Why do I need to know this?
Databricks is widely deployed in industry, and familiarity with it maps directly onto real work: ingestion patterns, medallion layering, governance, incremental processing, and serving curated datasets to analytics. Databricks has stated that over 60% of the Fortune 500 use platform in some capacity, and it reports over 20,000 organizations as customers.
Even when you are not working in Databricks, the core ideas it packages (Spark-based distributed compute, table formats like Delta, centralized catalogs/governance, declarative pipeline graphs) are the same ideas you will encounter across modern data platforms. Knowing how the platform abstracts a "typical company data environment" makes it easier to drop into new environments, diagnose problems, and deliver work without spending weeks rebuilding basic infrastructure understanding.
5. How Does Apache Spark Work With Databricks?
As mentioned in prior posts, Apache Spark is a distributed compute engine designed to process large datasets in parallel across a cluster. In Databricks, most workloads ultimately execute as Spark jobs on Databricks-managed compute.
Databricks does not run "vanilla Spark" by default. It runs Databricks Runtime, which includes Apache Spark plus platform-level optimizations for usability, performance, and security. On the performance side, some workloads can also use Photon, a Databricks-native vectorized engine that accelerates many SQL and DataFrame operations while remaining compatible with Spark APIs.
Those Spark jobs run on compute you choose in a few common modes:
- All-purpose clusters: interactive exploration (notebooks, ad-hoc analysis).
- Job clusters: production runs (created for a job, then terminated).
- Serverless compute (if enabled): Databricks abstracts cluster management further.
Why is this important? Cost, runtime, and failure behavior are determined by the compute mode and how long that compute stays alive. 
For example, consider a daily batch pipeline that prepares revenue and customer metrics for finance and leadership reporting. If this pipeline runs on an all-purpose cluster, compute can remain active outside the actual processing window, increasing cost without adding value. Running the same pipeline on a job cluster or serverless compute ensures resources exist only while the Spark job is executing, reducing waste and improving cost predictability.

How to Run It
Import the repo into Databricks Repos. In your Databricks workspace, go to Workspace → Repos → Add Repo (Git) and clone databricks-nyctaxi-lakehouse. You should see the project under Workspace/Repos/….
Run the Unity Catalog bootstrap (required). Open /unity/00_main_nyctaxi_catalogue_creator.ipynb and run all cells. This provisions the main_nyctaxi catalog, creates the raw, ref, and mart schemas, and creates the storage volume used by the project. (so the landing zone make sure that is clear)
Upload the NYCtaxi data set to the main_nyctaxi.raw using hte landing zone. This enables the raw parquet to be present in the bronze layer meaning we can now process it. 
Choose one Bronze ingestion path (do not run both). 
- Auto Loader path (using your own data): Put the NYC taxi dataset somewhere Databricks can read (UC Volume, DBFS, or S3/ADLS/GCS). Run /notebooks/01_auto_loader_bronze.sql.ipynb to load into main_nyctaxi.raw.taxi_raw. Then, in the DLT pipeline notebook, set Bronze to read/stream from main_nyctaxi.raw.taxi_raw and disable the sample source.

Configure the DLT pipeline. Open /dlt/pipeline_settings.json and verify:
The notebook path points to your local copy of /dlt/02_dlt_pipeline.sql.ipynb.
The target catalog and schema are correct (e.g., main_nyctaxi and the intended schema).
The storage location, pipeline edition, and other settings match your workspace's requirements.
Run the pipeline (Bronze → Silver → Gold). In the Databricks UI, navigate to Workflows → Pipelines, create (or select) a pipeline using the pipeline_settings.json configuration, and run it. This will execute the DLT pipeline, materializing the Silver tables and Gold outputs defined in 02_dlt_pipeline.sql.ipynb.
Validate Gold outputs. Open /sql/03_gold_queries.sql.ipynb and execute the provided queries against the Gold tables. Confirm that the Gold tables (daily KPIs) exist and that the queries return sensible results (non-empty, plausible values).
(Optional) Log metrics to MLflow. If desired, run /monitoring/mlflow_demo.py on a cluster.This script logs silver_rows plus a count of data-quality drop events pulled from the DLT event log. Ensure PIPELINE_EVENT_LOG_TABLE points to the correct, readable DLT event-log table in your workspace.

Note: this notebook does not configure access grants by default. If you need other users/groups to read or write these objects, add Unity Catalog GRANT statements as a separate step (either in this notebook or as a follow-up SQL cell).

Note: 02_dlt_pipeline.sql.ipynb uses fully qualified table names under main_nyctaxi.raw/ref/mart. If you need a different catalog/schema, update both the notebook and dlt/pipeline_settings.json; changing the JSON target alone will not redirect the pipeline outputs.

8. Validation Tests/Checks (and Why They Matter)
A pipeline can "succeed" and still be wrong. In real systems, most failures are silent: you rarely get a bright red error message stating that a step failed. Instead, issues surface later as missing rows, duplicated records, schema drift, or logic errors in downstream reports or dashboards. Because of this, validation must be applied throughout the lakehouse workflow so errors are caught as early as possible.
In this repo, validation checks are applied at every stage of the medallion architecture.
Bronze checks (did ingestion behave?)
In Catalog Explorer, start at main_nyctaxi.raw.taxi_bronze (and taxi_raw if Auto Loader was used).
 At this stage, the minimum checks are volume and shape:
Row counts look sane
Expected columns exist
Timestamps and partitions advance consistently from run to run

These checks confirm that ingestion is working correctly and incrementally.
Silver checks (did our contract boundary hold?)
Inspect the DLT pipeline UI for main_nyctaxi.ref.trips_valid.
Confirm that expectations were evaluated, invalid rows were rejected, and rejection counts are visible in the pipeline metrics.

Gold checks (did we compute stable business outputs?)
Run /sql/03_gold_queries.sqlagainst main_nyctaxi.mart.daily_kpis from a Databricks SQL warehouse or SQL Editor session.
The goal is not complex testing - it is invariants: the result is non-empty, dates are continuous, KPI values are within plausible bounds, and you are not generating duplicates.

Cross-run monitoring (do we detect regressions over time?)
If you run /monitoring/mlflow_demo.py, Silver row counts and counts of DLT data-quality drop events (queried via PIPELINE_EVENT_LOG_TABLE) are logged to MLflow. This turns correctness into a time series, making it easy to spot sudden volume drops, increased rejection rates, or unexpected shifts in Gold KPIs after a change. To derive actual dropped-row totals, aggregate the drop-related metrics in the event log rather than just counting drop events.
9. Data Contracts (What They Are and How This Repo Enforces Them)
A data contract is a defined set of rules specifying what values downstream tables are allowed to contain.
Data contracts are an increasingly common concept you should know for Databricks and data engineering in general, so it's best we cover it here with a short primer. In a lakehouse pipeline, enforcing a contract at the Silver stage ensures the "clean" data layer is deterministic for all downstream consumers (Gold aggregations, dashboards, or ML models). Without explicit contracts, invalid records can slip through unnoticed and distort outputs.
Databricks provides a native mechanism for data contracts in Delta Live Tables called expectations. Expectations let you define rules and specify actions on violations: you can log failures, drop invalid records, or fail the pipeline update when a rule is broken.
Contract in this repo: Defined in /dlt/02_dlt_pipeline.sql using DLT expectations.
Enforced rules (examples):
- vendor_id must be non-null.
- fare_amount must be >= 0.
Enforced at: The Silver validated table main_nyctaxi.ref.trips_valid.
Effect: Any row violating these rules is dropped from trips_valid, so downstream tables never see invalid data.

Note: With ON VIOLATION DROP ROW, violating rows are excluded from trips_valid and are not directly queryable as "failed rows." If you want to retain invalid records, implement a quarantine table explicitly (for example, define main_nyctaxi.ref.trips_invalid from trips_clean using the same predicates as your contract rules), and keep trips_valid as the contract-enforced dataset. For auditing/metrics (counts over time), query the DLT pipeline event log.
Demonstrating a contract break
(Using the Auto Loader path so we control the raw input)
Inject a bad record: Add a row to the raw CSV data where fare_amount = -5 (violating the non-negative rule) or vendor_id = NULL (violating the non-null rule), or both.
Re-run ingestion: Run /notebooks/01_auto_loader_bronze.sql.ipynb again. The bad row will land in main_nyctaxi.raw.taxi_raw.
Re-run the DLT pipeline: Run the pipeline (Workflows → Pipelines) so that trips_valid is recomputed.
Verify enforcement: The bad record will not appear in main_nyctaxi.ref.trips_valid. In the DLT UI, the expectation metrics will show additional failures (dropped records). Databricks' expectations interface lets you see how many records violated the rules and what action was taken.

Why this matters
This is the trust boundary between layers. Bronze can be messy (raw landing), but Silver is where we enforce correctness (typed, cleaned, contract-valid). Gold can then assume Silver is reliable; no negative fares or missing vendor IDs, for example.
Contracts also create an audit trail: expectation metrics quantify how much data was rejected and why. This provides operational guardrails - if the drop rate suddenly spikes, it is treated as a data incident to investigate, rather than a mysterious dashboard error.
(Optional) Trending in MLflow
The script /monitoring/mlflow_demo.py provides a minimal bridge from "pipeline ran" to "health is measurable".
It logs silver_rows each run, and it counts data-quality drop events (action = 'drop') from the pipeline event log defined by PIPELINE_EVENT_LOG_TABLE (the table must exist and be readable). This counts drop events, not total dropped rows. To compute dropped-row totals, query and sum the relevant drop metrics from the event log instead of using a simple .count():
# Querying the event log for drop metrics
spark.sql("SELECT * FROM event_log('<YOUR_PIPELINE_ID>') WHERE event_type = 'data_quality' AND action = 'drop'").count()
Over time, you can compare runs in the MLflow UI to detect regressions early, and you can extend the query above to aggregate drop metrics if you need exact dropped-row totals.
10. Cost and Compute Control
Using Databricks is not free, and as the scale increases, cost can become a primary constraint for an organization. A large part of using Databricks is figuring out how to lower total spend.
Databricks usage is measured in Databricks Units (DBUs). DBUs accumulate while compute is running; how usage is metered and billed depends on the product and cloud. In addition to DBUs, your cloud provider charges for the underlying VMs, storage, and network.
In practice, the main cost drivers are how long compute runs and which compute SKU you use.
Example Calculation:
In this tutorial, you might have:
An all-purpose cluster running for 20 minutes at C DBU/hour (15 min Auto Loader + 5 min MLflow demo).
A DLT pipeline compute running for 25 minutes at P DBU/hour.
A SQL warehouse running for 10 minutes at W DBU/hour.

The DBU consumption would be calculated as:
Total DBUs = C * (20/60) + P * (25/60) + W * (10/60)
Ensure clusters, pipelines, and SQL warehouses are stopped or configured to auto-terminate after the exercise.
Note: C, P, and W are placeholders for the DBU rates of the all-purpose cluster, pipeline compute, and warehouse compute. Use your workspace's actual DBU rates/SKUs to compute the real cost in your currency.
11. Next Steps / Possible Improvements
This repo is intentionally minimal. To make this production-ready, you might extend it in several ways:
Stronger data contracts: Add more expectations (e.g., value ranges, cross-field checks). Consider quarantining or storing rejected rows for analysis instead of just dropping them. Optionally, configure critical rules to fail the pipeline on violation.
Automated quality checks and observability: Enforce row-count thresholds and maximum drop rates (e.g., fail the workflow if Gold KPIs are outside expected bounds). Also, log expectation failure counts and drop rates to MLflow (or another metrics store) to enable trend monitoring.
Idempotent pipelines and backfills: Support parameterized reprocessing (e.g., by date range) and ensure reruns do not duplicate data or cause inconsistencies.
Environment separation and deployment: Use separate development/production catalogs or schemas. Deploy pipelines via configuration or CI/CD (e.g., Databricks Asset Bundles) instead of manual edits.
Cost and performance optimizations: Partition and optimize Silver/Gold tables for faster queries. Reinforce auto-termination and warehouse auto-stop to prevent idle costs.
